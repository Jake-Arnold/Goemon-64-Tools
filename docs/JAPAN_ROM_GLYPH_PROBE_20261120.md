# Japanese retail-ROM glyph atlas probe (Toolkit v0.11.74)

## Why an emulator-rendered atlas

The original decompressed Japanese N64 ROM SHA-1 is
`6f8745fecc3a5e7d4918c7a73353eb0726116ded`. The dialogue text
records use positive signed 16-bit values as character IDs. The exact
original Japanese **glyph bitmap storage, format and runtime lookup** have
not yet been established. It would be misleading to render a synthetic
bitmap grid, label it "ROM-extracted font", and infer characters from it.

Instead, `practice/dialogue_glyph_probe.py` builds ROMs that present
unresolved token IDs through **the actual original Japanese game renderer**.
This produces a trustworthy atlas when the generated ROMs are displayed
in Project64. No proprietary ROM bytes, font bitmaps or screenshots are
committed to the repository.

## Workflow

1. Import the original Japanese retail `.n64` / `.z64` through the
   Toolkit's Dialogue tab. This verifies the original ROM hashes and
   stores a 16 MiB retail and 32 MiB decompressed original.
2. Select **Japan** in the Dialogue tab, click
   **Generate Japanese glyph test ROMs** and choose a new, separate
   output directory.
3. The generator scans all statically indexed Japanese records and
   collects **positive token IDs not present in the current 215-glyph
   editable map**; known kana, uppercase Latin, known kanji and
   formatting controls are excluded. The previous source-only index
   contained 112 such IDs, with 1,632 occurrences. The actual number
   is recomputed each time from the pinned ROM and current mapping.
4. Suspect low-valued token **11** is excluded by default because its
   role as a printable character has not been demonstrated. It remains
   listed in the manifest, not silently marked resolved.
5. The other IDs are grouped in **7 columns × 4 lines per page**, using
   the original Japanese token stream with real `13` spaces and `-60`
   line breaks. With 111 testable IDs, this produces **4 separate
   16 MiB .z64 ROMs**. Each modifies **only Kai Highway area-name
   record 82 +0x18**, using the already tested relocation and original
   retail-ROM repacker.
6. In Project64, load each test ROM and enter Kai Highway. Capture the
   displayed four lines; compare them against `jp-glyph-probe-guide.html`,
   or use the exact position list in `jp-glyph-probe-manifest.json`.
7. Match positions to Unicode only after reading the original renderer's
   actual glyphs. Some IDs may be non-printing, composite glyphs or
   symbols; maintain a separate status until verified.

## Geometry limitation

Kai Highway uses a **two-line painted window**. Earlier user Project64
captures proved that manual `-60` line breaks place additional text
**below** the green window without enlarging the artwork. Four lines
are legible in that demonstration but may overlap different scene
backgrounds. The generated glyph probe keeps lines narrow (seven glyphs
separated by spaces) to reduce horizontal overflow. Characters with
unusual advances can still overlap or be hidden. This is a validation
probe, **not a proof of native Japanese textbox geometry**.

## Input/output safety

- Input originals are SHA-1 verified on every run.
- The generator never changes the persistent original ROM library,
  source ROM, or existing staged user dialogue edits.
- It writes to a temporary folder in the selected output directory;
  output filenames already present cause refusal rather than overwrite.
- Every produced ROM includes the original proper CIC checksum from the
  existing Japanese retail repacker and its SHA-1 is placed in the
  manifest. No independent emulator screenshots are generated by Python.
- The producer does not require TkDND, GUI clipboard, emulator memory
  access, networking or any new dependency beyond the existing Japanese
  retail-ROM builder (`lzkn64`).

## Remaining direct-extraction research

To produce PNG bitmaps automatically without an emulator, trace the
Japanese renderer's glyph lookup to its backing texture resource and
recover the exact N64 texture format, dimensions, palette and token
indexing. Raw ROM texture-like regions were observed but **not
proven** to be the dialogue glyph atlas. Do not invent addresses, token
stride or graphics from candidate raw bytes.
