# Experimental native Mupen64Plus Frame Inspector

The native research frontend runs the Mupen64Plus core in a **separate child process on its main thread**, leaving Tk in the parent. It launches its own session; it does not attach a stock emulator already running. A Linux-only Japan-0 Dashboard adapter can access the inspector-owned child’s bounded RAM without external process discovery. On Linux source mode, open the main toolkit **Frame Inspector → Mupen64Plus (native)**. The Dashboard **Advanced connection → Open native Mupen64Plus Frame Inspector** shortcut selects this same embedded page. Switching between backend pages or other toolkit tabs leaves the native session and traces intact. Linux Japan-0 on core 2.6.0 can connect its managed child through the Dashboard; other external attachment backends remain unchanged. The native frontend requires a Mupen64Plus 2.6.0 core (or another 2.x core advertising debugger support), matching native graphics/audio/RSP plugins, data files, Python 3 with Tk, and a C11 compiler for the scripted input plugin. No original game files are included. Use only your own original USA or Japan retail revision-0 ROM.

## macOS (source mode; standalone launch retained)

Install Xcode command line tools (`xcode-select --install`) if needed. With Homebrew installed, install Mupen64Plus and Python/Tk for your chosen Python version. The packaged 2.6.0 core can use the documented RDRAM pointer API without the optional debugger. Other 2.x releases must advertise debugger capability for typed reads. CPU breakpoints will require a `DEBUGGER=1` build in a future implementation. Do not disable macOS security protections. Match architectures (arm64 or x86_64) of Python, core and all plugins. Locate the installed core, plugins, data directory and SDK header `m64p_plugin.h` using `brew --prefix mupen64plus` and `brew list mupen64plus`; formula layouts vary. Check `python3 -m tkinter` before launching. Use the header from the installed core SDK, or matching upstream SDK source if headers are not packaged.

The source toolkit builds or refreshes its bundled input bridge asynchronously at startup when needed. It uses the installed matching SDK and C compiler; it does not install dependencies. You can manually build against a chosen SDK directory if discovery fails:

```sh
bash scripts/build_mupen_input.sh /path/to/mupen64plus-sdk
bash Run-Mac.sh
```

## Linux (source mode, integrated toolkit)

On Debian/Ubuntu with Mupen64Plus 2.6.0 packages available:

```sh
sudo apt install mupen64plus-ui-console libmupen64plus-dev mupen64plus-video-rice mupen64plus-audio-sdl mupen64plus-input-sdl mupen64plus-rsp-hle python3-tk python3-psutil build-essential
bash Run-Linux.sh
```

Select **Frame Inspector → Mupen64Plus (native)**. Library detection checks bounded `/usr` and `/usr/local` directories including multiarch plugin locations and the Debian shared-data directory. For a custom installation, browse to its matching core and libraries manually. The startup build reuses a current binary, recompiles missing or stale ones, and reports SDK/compiler errors without blocking the toolkit. Use `MUPEN_SDK=/path/to/sdk bash Run-Linux.sh` or `bash scripts/build_mupen_input.sh /path/to/sdk` to choose a matching SDK. The compile is local and atomically replaces the default binary only on success. The native standalone launch (`python3 -m practice.mupen_native_ui`) is retained. The game window remains a separate native SDL window; the inspector controls are embedded.

The native embedded page is disabled on Windows, frozen builds and read-only sessions; the Project64 page retains its existing access policy. Existing Project64 and native recomp connections are unchanged. No changes to external-process permissions are needed.

## Setup and operation

Use **Find Mupen64Plus installation** to prefill installed files, or browse manually. The embedded page tries discovery once when first opened. Choose the exact ROM, `libmupen64plus` core library, native GFX, audio and RSP plugin libraries, and the **custom Goemon input plugin** just built (not the stock SDL input plugin). Choose the Mupen64Plus shared-data directory and a research configuration parent directory; the frontend uses a dedicated `goemon-native-session/research-saves` subdirectory. It selects pure interpreter mode, disables randomized PI/SI timing, and rejects non-debug cores other than 2.6.0. This changes timing relative to normal randomized configurations, so compare only sessions with identical settings. Launch session; the setup panel collapses automatically to leave space for traces. Show setup reopens it. Use Hold input while running to navigate, or Pause then Step +1 / Run timeline. The optional `physical_input` field selects the installed stock SDL input library, not the custom Goemon plugin. Startup automatically rebuilds the default custom Goemon input library after relevant source updates. **Play with controller** resumes using the stock SDL provider (keyboard and mapped controller); Hold input, Resume neutral, Step and Run timeline select exclusive scripted P1 input. Recording requires scripted mode; physical input is not included in traces. The input plugin presents only P1, no controller pak. The stock SDL plugin uses the isolated research config; normal installation mappings may need to be copied into its Input-SDL-Control1 section before launch. Resume resets input to neutral; held input remains active until changed. Closing the UI requests normal emulator stop through its private inherited stdin; no network server is started.

Watches may be entered before launch or edited during a session. Pause and stop recording, then select **Apply watches (paused)**. Changing the schema clears the previous trace only with explicit confirmation; export first if needed. Invalid changes preserve the previous watch set and rows. The next core callback samples the new schema. The **JP controller preset** fills in the ten catalogue-backed watches established by the Japanese horizontal/vertical/C-Up tests. The preset is not approved for USA.

Each line is `name u8/s8/u16/s16/u32/s32/f32 hex_address` or `name u16 @catalogue_id`. At most 24 watches. An explicit pointer chain such as `example f32 80001000->5C->20` means read a u32 guest pointer at 0x80001000, add 0x5C, read another u32 pointer there, add 0x20 and read the final float. This address is illustrative, not a player root. A `@catalogue_id` root requires a registered 4-byte field. Every hop and final read must be aligned within the first 4 MiB of KSEG0 RAM, with at most four dereferences; invalid/null pointers return unavailable. A valid address does not prove the object is still the player. No writes from the watch editor. On core 2.6.0, the documented `DebugMemGetPointer` supplies native uint32 words regardless of debugger capability, matching the Dashboard managed reader layout; other supported debugger cores use typed reads and require readable RDRAM flags. Failed reads show individual reasons in the report and a summary in the status. Reads are sampled at core callbacks. **Locate Player (JP)** is a paused, read-only first-4-MiB snapshot search for the Japan-0 original callback pair `801D0F54` at task+8 and `801D1228` at task+10, with action/object/context pointer and character checks. A unique structural candidate fills the Ebi Slide preset and clears old traces only with confirmation. Verify movement and transformation before interpreting it as the active player. Each subsequent sample checks the callback pair; a changed signature makes task watches unavailable until relocated. No automatic selection of ambiguous matches. Relocate after scene changes even if the signature remains present.

Watch and timeline editor drafts and the step count are saved locally in `native-inspector.json` alongside launcher preferences, not in Git. Restored generated Locate Player watches are **not** installed into a new emulator until the player is located again; manually entered absolute watches are still user-supplied hypotheses. Editor preferences do not retain active buttons/stick state. Since v0.11.94 the worker atomically checkpoints the latest nonempty trace to `goemon-native-session/research-traces/trace-<pid>-<timestamp>.json` below the selected config directory; a new capture in the same session replaces the checkpoint, while Clear trace preserves it. **Recover latest trace** copies it, including after a stalled command or child exit. The checkpoint is local only; retain important captures separately.

Timeline syntax accepts single relative frame numbers or inclusive ranges (no overlaps), e.g. for a 600-frame batch:

```
1-120 - 80 0
121-126 - 0 0
127-132 CU 0 0
133-600 - 0 0
```

Unspecified frames use the manual buttons/X/Y controls. **Step +1** ignores the timeline and uses those controls, whereas **Run timeline** uses the specified count and timeline. This is an illustrative transformation timing control, not a proven Ebi Slide sequence. Steps call native `M64CMD_ADVANCE_FRAME` and wait for the native frame callback **and** paused state. A batch rejects extra callbacks, timeouts and oversized input sequences (max 600). Each callback records P1 plugin polls since the previous callback (for a stepped batch the counter resets at the step request) and the last requested input, not proof that the game consumed it. Record toggles continuous capture, with a bounded 3,600-row buffer; step captures even with Record off. Long step batches transfer captured rows incrementally and return to paused state. Dedicated protocol stdout is isolated from C/Python native logs, which are independently drained on stderr. Bounded packets carry row deltas; unchanged status polls no longer resend trace buffers. Decode errors are explicit, and a 20-second no-response watchdog blocks further commands and paused memory edits, but retains recovery. Stop emulator after confirming if a session is genuinely stuck; this can lose unsaved gameplay. The trace table updates in incremental chunks; **Copy trace** copies all original captured rows with tab-separated headers, even while the table is still rendering. Click the table then Ctrl+A/Ctrl+C (Cmd+A/Cmd+C on macOS) to copy all, or select specific rows and copy. Copy is from original capture, not comparison display. Export CSV/JSON, compare with a compatible JSON trace by relative row, orange for changes and red for differences. Raw traces stay private; don't commit them.

## Dashboard connection (Linux Japan-0, core 2.6.0)

Launch the inspector's game, enter normal gameplay, then choose Japan on the Dashboard, select Mupen64Plus or Auto, leave PID blank, and click Connect to game. The parent uses metadata from the private child pipe, the exact retail ROM identity and three independent main-code probes; it rejects stale sessions and limits transfers to 4 MiB of guest RDRAM. No scan or OS permission change is needed for the owned child; if procfs access is refused, attachment fails rather than weakening permissions. Pause the inspector and stop recording before Live Memory or mapped unlock edits. In the isolated research config, stock pause, frame-advance, reset, save-state, load-state and speed-limiter-toggle hotkeys are disabled; use the inspector controls. Existing expected-value and readback checks remain. Export/clear traces before deliberately changing experiment state. Native debug-menu and instant warp shortcuts and continuous freezes are excluded for this session. Ending the child detaches the Dashboard. These paths are synthetic-tested, not yet live gameplay-verified.

## Mini Ebisumaru ability grant (Japan-0, core 2.6.0 only)

Enter normal gameplay with Ebisumaru available, export and clear the trace, stop recording, and pause. Click **Unlock Mini Ebisumaru (JP)** and confirm. One neutral core frame advances; the native frame callback resolves the existing Japanese inventory byte and original script grant word from the catalogue, checks the pinned mapping, refuses unexpected nonbinary word values, sets the word to 1 only if it was 0, and verifies readback. No forced transformation, party membership, event flags, action or movement edits. The status reports the grant result, not a continuously monitored ability value. Switch to Ebisumaru and use C-Up normally. This changes the research session's live saved-data state and may persist if saved; it does not edit the original ROM. Do not use in title/menu/loading states. Native gameplay acceptance remains untested for this grant.

## Boundaries and current limitations

A Mupen64Plus **core frame** is not a Goemon player update. An emulator pause command may stop between frames. The first recorded stepped sample is the next core callback; input polling may have occurred before or after a given game update. The trace does not establish the Ebi Slide mechanism. A future calibrated player-update hook must independently correlate execution, consumed inputs and player task identity. CPU breakpoints, true logic-update stepping, stock process attachment through this frontend, and Dashboard RAM attachment on USA/macOS are **not implemented**. The Linux Japan-0 managed attachment is limited to the first 4 MiB, paused manual edits, and existing mapped unlocks; freezes and native warps are excluded. The native frontend is source-mode only. Earlier user-supplied macOS traces demonstrated controller polls, game-side input and dynamic watch reads. User confirmed the integrated Linux game runs and located both Japanese callbacks at 8016F788/8016F790 through Dashboard Find a value; the v0.11.91 Frame Inspector returned None. User subsequently confirmed populated watches, completed a 600-frame batch, and captured ordinary mini-to-normal transformation. Some batches still stalled awaiting results in v0.11.93. The v0.11.94 transfer and managed states are synthetic-tested but await live validation. Mock tests exercise the ABI-facing plugin/controller and frontend state machine; they cannot establish live compatibility. See upstream [2.6.0 RDRAM implementation](https://github.com/mupen64plus/mupen64plus-core/blob/2.6.0/src/device/rdram/rdram.c), [2.6.0 pointer API](https://github.com/mupen64plus/mupen64plus-core/blob/2.6.0/src/api/debugger.c), [frontend API](https://github.com/mupen64plus/mupen64plus-core/blob/master/src/api/m64p_frontend.h), [debugger API](https://github.com/mupen64plus/mupen64plus-core/blob/master/src/api/m64p_debugger.h), [plugin API](https://github.com/mupen64plus/mupen64plus-core/blob/master/src/api/m64p_plugin.h), and [native frame callback/pause implementation](https://github.com/mupen64plus/mupen64plus-core/blob/master/src/main/main.c).


### Managed savestates (core 2.6.0)

Pause and stop recording. Choose slot 0–9 (default 0); **Save state (F5)** or **Load state (F7)** in the inspector, with inspector keyboard focus. The stock emulator-window save/load mappings are disabled to prevent concurrent state jobs. Slot files remain in the isolated `research-saves` directory, compatible with an earlier F5 slot save in that same config and ROM. The load confirmation warns that current gameplay and the active trace will be replaced; the prior latest trace checkpoint remains available. Restore invalidates applied watches and comparison; editor drafts remain, so Locate Player or Apply watches again. State jobs execute on core interrupts: the inspector advances bounded neutral frames until the load/save completion callback and paused boundary are acknowledged. This is not an exact zero-frame restore. A failed or unacknowledged job is explicit; unresolved jobs quarantine further operations until the session is stopped. Never use arbitrary state files from an untrusted source. No game data or savestates are committed.
